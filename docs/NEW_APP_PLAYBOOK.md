# New App Playbook

Step-by-step instructions for adding a new internal app to this platform. Written so a human **or an AI agent** can follow it exactly. Do the steps in order and do not skip any. If a step looks wrong for your app, stop and ask a human; don't work around it.

Throughout, replace:

- `<id>` with the app's URL slug: lowercase, hyphenated (e.g. `feature-flags`)
- `<Entity>` with the Prisma model name in PascalCase (e.g. `FeatureFlag`)
- `<entity>` with the camelCase Prisma client accessor (e.g. `featureFlag`)

The reference implementations are **Refunds** (`lib/apps/refunds`, maker-checker approvals) and **KYC** (`lib/apps/kyc`, a state machine plus PII masking). When in doubt, copy their patterns.

---

## 0. Ground rules (non-negotiable)

1. **Every API route calls `requireRole(user, [...])` from `@/lib/platform/rbac` as the first call in every handler.** Only the `route()` wrapper may come before it. Do not read the body, params, or database first.
2. **Every route handler that writes data calls `audit()` from `@/lib/platform/audit`**, inside the same `prisma.$transaction` as the write.
3. **Never update or delete `AuditLog` rows.** No such API exists, and DB triggers reject it.
4. **Anything needing a second person goes through `createApprovalRequest()`** (`@/lib/platform/approvals`). Never write your own approval logic. The platform enforces "approver ≠ requester".
5. **Writes go through API routes in `app/api/apps/<id>/`.** Server Actions (`"use server"`) are forbidden, and the guardrail test fails on them.
6. **Sensitive fields are masked on the server** before data leaves a service function. Never send raw rows containing PII to the client or put PII in audit `before`/`after`.
7. **External systems are called only through a client in `lib/integrations/<name>.ts`.**
8. **Do not edit `lib/platform/*` or weaken `tests/guardrails.test.ts`** as part of an app PR. If the platform is missing something, raise it separately.

Roles: `reviewer` (makers / day-to-day operators), `approver` (checkers, may see PII), `admin` (platform admins: audit log, configuration). `admin` is **not** a superuser and does not imply the other roles.

## 1. File layout

Create exactly these files (plus any extra components your UI needs, kept in the app's page folder):

```
prisma/schema.prisma                       # add your model(s)
prisma/migrations/<timestamp>_<id>/        # generated by Prisma
lib/apps/<id>/manifest.ts                  # app metadata + approval handlers
lib/apps/<id>/service.ts                   # all business logic and DB access, plus zod schemas
lib/integrations/<vendor>.ts               # only if you call an external system (stub it)
app/apps/<id>/page.tsx                     # server-component page
app/apps/<id>/<Something>Form.tsx          # optional "use client" components
app/api/apps/<id>/route.ts                 # GET list / POST create
app/api/apps/<id>/[id]/route.ts            # optional: GET one / PATCH / DELETE
app/api/apps/<id>/[id]/<verb>/route.ts     # optional: state transitions, e.g. /toggle
tests/<id>.test.ts                         # required tests (see step 7)
```

Then edit `lib/apps/registry.ts` (step 6) and `prisma/seed.ts` (step 8).

---

## 2. Data model

1. Add your model to `prisma/schema.prisma` under a `// ---------- App: <Name> ----------` heading.
   - `id String @id @default(cuid())`, `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`.
   - SQLite has no enums: use `String` and document the allowed values in a `///` comment. Validate them with zod in the service.
   - Store JSON as `String`.
   - Mark PII fields with `/// PII:` comments.
2. Generate the migration:
   ```bash
   npx prisma migrate dev --name <id>
   ```
3. Never edit an existing migration. Always add a new one.

---

## 3. Service layer: `lib/apps/<id>/service.ts`

All business logic lives here. Route files stay thin.

```ts
import { z } from "zod";
import type { Db } from "@/lib/db";
import type { CurrentUser } from "@/lib/platform/auth";
import { ConflictError, NotFoundError } from "@/lib/platform/errors";

export const <ENTITY>_ENTITY = "<Entity>";           // used as audit/approval entityType

export const create<Entity>Schema = z.object({ /* every field, with limits */ });
export type Create<Entity>Input = z.infer<typeof create<Entity>Schema>;

export async function list<Entity>s(db: Db, user: CurrentUser) {
  const rows = await db.<entity>.findMany({ orderBy: { createdAt: "desc" } });
  return rows; // if the model has PII, map through a present() function first (see KYC)
}

/** Called inside a transaction. Returns before/after snapshots for the route to audit. */
export async function update<Entity>(tx: Db, user: CurrentUser, id: string, input: Update<Entity>Input) {
  const before = await tx.<entity>.findUnique({ where: { id } });
  if (!before) throw new NotFoundError();
  const after = await tx.<entity>.update({ where: { id }, data: input });
  return { before, after };
}
```

Rules:

- Functions that write take `tx: Db` as the first argument, so the route can wrap them in a transaction together with `audit()`.
- Throw the typed errors from `@/lib/platform/errors` (`BadRequestError` 400, `ForbiddenError` 403, `NotFoundError` 404, `ConflictError` 409). The `route()` wrapper turns them into JSON responses.
- For finer-grained authorization (e.g. one action needs `approver`), call `requireRole(user, [...])` again inside the service, as in `lib/apps/kyc/service.ts`.
- **State machines:** declare every legal transition in a table (see `lib/apps/kyc/state-machine.ts`), look the transition up on the server, throw `ConflictError` if it isn't found, and use a conditional `updateMany({ where: { id, status: current.status } })` to prevent races.
- **PII:** write a `present<Entity>(row, user)` function that masks fields unless `hasRole(user, "approver")`, plus an `auditSnapshot(row)` that omits PII. Every read path returns `present…()` output (see `lib/apps/kyc/present.ts`).
- **Side effects you trigger** (e.g. executing a payment after creating a record) are audited inside the service with `audit({...}, tx)`.

### 3a. If the app needs maker-checker approval

1. In the service, when the action needs approval, persist the entity in a pending state and call:
   ```ts
   await createApprovalRequest(tx, {
     entityType: <ENTITY>_ENTITY,
     entityId: entity.id,
     payload: { /* exactly the values the checker is approving */ },
     requestedBy: user,
   });
   ```
2. Export an `ApprovalHandler`:
   ```ts
   export const <entity>ApprovalHandler: ApprovalHandler = {
     summarize: (payload) => `…one line for the approvals inbox…`,
     async onApproved({ tx, request, payload, decider }) {
       // re-load the entity, check it is still pending AND still matches payload, apply, audit({...}, tx)
     },
     async onRejected({ tx, request, decider }) {
       // mark rejected, audit({...}, tx)
     },
   };
   ```
3. Register it in your manifest (step 5). Don't build an approve endpoint: decisions go through the generic `POST /api/approvals/:id`, which enforces the approver role and requester ≠ approver, and audits `approval.approved` / `approval.rejected`.

### 3b. If the app calls an external system

Create `lib/integrations/<vendor>.ts` exporting a typed client object with a stubbed implementation that returns realistic success responses with no network access (see `payments.ts`, `kyc.ts`). Pass an idempotency key for anything that moves money or changes state. Read credentials only from env vars, never hard-coded.

## 4. API routes: `app/api/apps/<id>/.../route.ts`

Copy this template exactly. The order of the first lines matters, because the guardrail test checks it.

```ts
import { NextResponse } from "next/server";
import { prisma } from "@/lib/db";
import { <ENTITY>_ENTITY, create<Entity>, create<Entity>Schema, list<Entity>s } from "@/lib/apps/<id>/service";
import { audit } from "@/lib/platform/audit";
import { getUserFromRequest } from "@/lib/platform/auth";
import { parseBody, route } from "@/lib/platform/http";
import { requireRole } from "@/lib/platform/rbac";

export const GET = route(async (req) => {
  const user = requireRole(await getUserFromRequest(req), ["reviewer", "approver", "admin"]);
  return NextResponse.json(await list<Entity>s(prisma, user));
});

export const POST = route(async (req) => {
  const user = requireRole(await getUserFromRequest(req), ["admin"]);   // 1. authorize FIRST
  const input = await parseBody(req, create<Entity>Schema);            // 2. validate
  const result = await prisma.$transaction(async (tx) => {             // 3. write + audit atomically
    const created = await create<Entity>(tx, user, input);
    await audit(
      { actorId: user.id, action: "<id>.created", entityType: <ENTITY>_ENTITY, entityId: created.id, after: created },
      tx,
    );
    return created;
  });
  return NextResponse.json(result, { status: 201 });
});
```

For dynamic segments, the handler signature is `route(async (req, { params }: { params: Promise<{ id: string }> }) => { … })`. Call `requireRole` **before** `await params`.

Audit `action` naming: `<id-or-entity>.<past-tense verb>`, e.g. `flag.created`, `flag.toggled`, `refund.executed`. Include `before` for updates and deletes, and `after` for creates and updates.

Import the manifest and add it to `APPS`. That's all the registration there is: the left nav, the home page cards, and approval routing all read from `APPS`.

## 7. Page: `app/apps/<id>/page.tsx`

```tsx
import { Card, Forbidden, PageHeader, td, th } from "@/components/ui";
import { prisma } from "@/lib/db";
import { getApp } from "@/lib/apps/registry";
import { list<Entity>s } from "@/lib/apps/<id>/service";
import { getPageAccess } from "@/lib/platform/page";
import { hasRole } from "@/lib/platform/rbac";

const app = getApp("<id>");

export default async function Page() {
  const { user, allowed } = await getPageAccess(app.roles);
  if (!allowed) return <Forbidden roles={app.roles} />;
  const rows = await list<Entity>s(prisma, user!);
  // render a table; show write controls only if hasRole(user, "<role>")
}
```

- Hiding buttons is UX only. The API route is the real gate.
- For buttons that POST to an API route, use `components/ActionButton.tsx`. For forms, copy `app/apps/refunds/RequestRefundForm.tsx` (a `"use client"` component that `fetch`es the route and then calls `router.refresh()`).
- Client components must not import `@/lib/db` or `@/lib/platform/{audit,approvals,auth}`.
- Reuse `PageHeader`, `Card`, `StatusBadge`, `th`, `td` from `components/ui.tsx`.

## 8. Seed data: `prisma/seed.ts`

Add realistic records for the new model using `faker`. Use fake-only ranges for anything identity-like (e.g. SSN area numbers 900–999). Write one `seedAudit(...)` entry per seeded record.

## 9. Required tests: `tests/<id>.test.ts`

Use the helpers in `tests/helpers.ts`: `ensureUsers()`, `req(method, path, { as, body })`, `params({...})`, `auditFor(entityId)`. Call route handlers directly, the way `tests/refunds.test.ts` does. Every app must have tests proving:

1. **Happy path** for every write route, with status code, DB state, and the exact audit actions (`expect((await auditFor(id)).map(l => l.action)).toEqual([...])`).
2. **RBAC**: each write route returns `401` with no user and `403` for each role that must not be allowed (including `admin` if admins shouldn't write).
3. **Validation**: a bad body returns `400`.
4. If you use **approvals**: the requester cannot approve their own request (`403`), a different approver succeeds, and rejection leaves no side effects.
5. If you have a **state machine**: a test enumerating the allowed transitions table, and an invalid transition returns `409`.
6. If you have **PII**: the raw JSON response for a non-approver does **not contain** the raw value (`expect(await res.text()).not.toContain(raw)`), and an approver gets the full value. Audit entries don't contain PII.

`tests/guardrails.test.ts` automatically picks up your new routes and your manifest. You don't need to edit it.

## 10. Verify, then open the PR

Run all of these and make sure each passes:

```bash
npm run lint
npm run typecheck
npm test
npm run db:seed && npm run dev   # click through as each seeded user
```

Manual check: switch between Alice (reviewer), Carol (approver), and Erin (admin) and confirm each sees and can do only what they should, and that every write you made appears on `/audit` as Erin.

PR description must include: what the app does, its roles matrix (role → allowed actions), which actions are audited, whether it uses approvals or holds PII, and any new integration stubs.
